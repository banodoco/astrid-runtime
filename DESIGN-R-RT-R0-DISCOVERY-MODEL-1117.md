## 1. Determination and decisions

**A finite re-read can preserve the authorization boundary and cover a genuine publication gap. The retained receipts do not establish that waiting would repair the direct Linux/macOS failures.** R0 legitimately leaves a plain owner marker after withdrawing discovery during shutdown. Waiting for publication cannot recover an exited publisher or authenticate a still-draining owner. Pinokio's startup observation is a separate consumer phase with the same missing-file symptom.

Recommend one Runtime-owned state model and a narrowly bounded publication observation, subject to the interface decisions below. While observing, no operation gains interruption authority. Success requires a separately published, complete discovery for the original exact PID, birth identity, Runtime instance, selected realm and canonical root, followed by the existing authenticated endpoint, custody and interruption fences. Malformed data, mismatch, unresolved identity and timeout refuse; persistent absence remains refused. No synthesized discovery, lock-only stop, service-state fallback or automatic `up` recovery is introduced.

| D2: publication grace | Permit observation only for actual missing-file startup/publication state, with the fixed original identity and a single finite budget (§5). ## 4. One state model and decision table

Let **T** be `(PID, process_birth_id, runtime_instance_id, realm_id, canonical realm_root)`, bound also to the selected installation's canonical data/support root. Birth strings must match exactly between marker and discovery; comparison to the OS uses Runtime's proven native identity comparator, never string weakening or PID-only inference. Let **L** be validated owner-marker data and **D** an independently read discovery record. D supplies an HTTP loopback endpoint; health and authenticated realm/instance checks plus native custody validate that endpoint. A file's presence is not authentication.

These states are *observations*, not new persistent marker values or a new schema. An observer cannot distinguish every producer phase from file presence alone. OS observations may veto an action or prove absence under an existing path; they do not turn L into live stop authority.

## 5. Bounded publication observation proposal

Proposed interruption publication grace: **5.0 seconds**, poll interval **100 ms**, **one deadline per top-level attempt**, measured by a monotonic clock. These values are a bounded initial policy choice for review, not an evidence-derived startup SLA. A caller's smaller remaining budget wins. Invalid/non-finite/negative budgets refuse; no environment variable may enlarge this policy. The grace bounds waiting for a file; ordinary stop, authenticated requests and kernel-lock acquisition retain their own explicit budgets. Do not advertise a five-second bound for the whole update.

1. Validate selected paths/catalog/realm/root. Read L/D with existing private regular-file and platform ownership/ACL protections; keep missing, malformed and unreadable distinct. Enter grace only for actual D absence and a complete ordinary marker anchored to T. No grace for stopping/completed-stop/restore states, foreign roots, malformed data or a present mismatched D. No kernel sidecar lock, work fence or manager mutation is acquired while waiting.
2. Freeze T and selected data/support/realm context. Each iteration checks cancellation/deadline and rereads catalog selection, L and D. Never reset the deadline because the process looks alive or a file changes. If T, selection or marker state changes, refuse. A same-T ordinary marker may gain the Runtime-produced embedded discovery member during normal current publication; validate its shape and same-T binding, but do not use it as D or as endpoint authority. Other unexpected semantic marker changes refuse.
3. While D is genuinely absent and L remains eligible, wait at most `min(100 ms, remaining)`. No signal, process spawn, service-manager action, file creation/repair/unlink, database write, completed-stop receipt or fallback endpoint lookup occurs. A discovered replacement, malformed record or read error ends this attempt immediately. Observation cannot prove an unseen ABA transition; final Runtime revalidation remains mandatory.
4. When D appears **before** the deadline, require complete supported discovery and exact T/root agreement. Read L–D–L and selected context consistently; compare both L observations to the anchor. The two publications are independently read, not filled from one another. D's endpoint then goes through ordinary loopback, native birth, instance/realm authentication and custody validation. If those checks fail or remain unknown, refuse; do not keep retrying mismatches. Publication-ready is not service-ready or stopped.
5. Re-enter the ordinary interruption path. `_preflight_owner_interruption` still performs work admission. Under `_bootstrap_mutex`, reread everything and retain `_interrupt_owner_locked`, `_fenced_stop_and_manager` and boundary pre-signal checks. Disappearance/replacement there refuses without a second grace. The observation result is not a cached capability and never skips a validator. Pending or timed-out observation leaves no new sidecar or intent.

For Pinokio startup, the same observer may also wait in the initial both-files-absent state within **min(5 seconds, the existing launch deadline's remaining time)**, adopting the first complete ordinary T only as an observation anchor. Once anchored it never retargets. The startup deadline is not restarted and no extra five-second allowance is appended. This phase distinction changes what can be awaited, not what is authorized. A Runtime publication observation result is diagnostic; the real engine/provider still proves readiness, custody and action settlement separately.

The initial Runtime implementation should centralize this in a private read-only helper used before interruption serialization, without changing existing boundary validators. Exposure to consumers is the explicit Q1 interface decision. Do not repurpose `doctor.healthy`, which can be true without discovery, as the new success predicate. Do not poll by rerunning `down`, restart, the installer transaction or `POST /v1/update`.

## 6. Recovery gap and cross-owner decisions

**Q1 — M-INT decision:** approve one additive Runtime-owned read-only observation interface for M-R1FIX/M-PIN, or initially keep grace internal and leave consumers with refusal. Proposed interface: `await_owner_publication(paths, boundary, phase, timeout_seconds)` with `phase=interruption|startup`; monotonic budget capped as above; result contains `publication_observed` plus T/context and sanitized elapsed/read status, never `safe_to_stop`, `stopped` or credentials. Errors distinguish absent-timeout, malformed/unsafe, mismatch/changed and unresolved authentication. M-PIN's subprocess needs an installed Runtime CLI wrapper around this exact helper, with finite exit status/JSON errors; **the wrapper name, package availability for R0-installed environments and versioned result shape must be agreed before implementation**. A caller must use a published supporting Runtime, not pin the design or PIDNS candidate. No HTTP API, bridge payload or discovery schema change is presumed.

**Q2 — concrete interface, decision owner M-INT:** the 01:14:08Z directive already selects a narrow already-stopped R0 admission. What verifiable retained service-definition/program/arguments context will M-R1FIX supply, and how will Runtime itself obtain a complete fresh owner/descendant census and realm-lock absence at both guards and the final work fence? Caller booleans such as `already_stopped`, `manager_dead` or `owner_active:false` are inadmissible proof. M-RT must name the supported native census/absence mechanisms and unavailable-result behavior before coding; M-R1FIX must identify the exact private selected-version/service artifacts and preservation rules. A file named like a realm lock being absent is not proof that its kernel ownership is absent. No broad new owner contract is presumed. The two directions have different status:

- **Pre-admitted handoff (alternative, not selected/approved):** while D still exists, Runtime authenticates T/endpoint and work state, retains custody/operation binding and records durable stop intent; only then may a validated manager action withdraw the service. Runtime owns subsequent drain/absence, replacement rechecks and cleanup. The installer supplies a service adapter; it does not mint authority. This may require changing the currently protected “Runtime stop then manager callback” ordering or adding a callback that only inhibits respawn.
